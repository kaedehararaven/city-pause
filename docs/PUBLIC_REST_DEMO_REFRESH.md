# 王府井休息案例补充

## 后续展示修订

用户明确指定compact休息Demo只展示一条咖啡厅方案，并恢复历史iGELATO到王府井书店分馆方案。`restShowcase.ts`仅通过PublicReplay注入的回调生效：保留算法返回的第一条咖啡厅路线，对指定甜品店/书店使用原构造器和历史缓存重新验证时间及约束，不传任何在线fetcher。未通过验证不强行展示。

正式REAL链路没有此回调，不改排序、去重、首站规则。原算法结果不被修改；审计以demoSelection分别记录原结果数量与展示数量。页面明确标注指定历史案例。下文三条咖啡厅结果是展示修订前的正常算法输出，不再等同于当前Demo展示。

本轮只更新离线数据与回放接线，不改正式供给、Goal Match、排序、停留规则或路线算法。

## 真实采集

- 起点复用已采集的王府井商业街 BD-09 坐标，不使用用户定位。
- 600米范围，query=咖啡厅$书咖$茶馆，一次合并 Search、只读一页。
- 依据真实 classified_poi_tag 验证并执行完整标签最多5条，得到5家咖啡厅、4家茶馆；本次没有取得有效书咖。
- 补5家咖啡厅的起点路线，再由当前构造器在6次共用请求预算内补站间路线。茶馆保留为真实供给记录，但本次没有补其去程，不能声称都已具备可推荐路线。
- 总成本 Search=1，walking=11（去程5、站间6），Detail=0；初次本地服务未启动导致连接拒绝，不计百度请求。
- 原始适配数据写入 public-rest-capture.json，包含查询、半径、时间、候选、请求数和真实有向路线。

## 回放范围

仅compact休息候选池优先使用本次以王府井为中心采集的新记录，然后合并旧记录并再次限制每标签5个。原公开起点候选池不替换。这里是离线采样数据更新，不是对咖啡厅增加推荐权重。旧路线事实仍保存并可复用。

候选池审计和地点计数随所选案例更新；新数据不进入线上缓存。所有回放均不请求网络。

## 结果

90/120/150/180分钟休息均产生3条咖啡厅到书店的路线，首站按正常默认排名为阿拉比卡APM、星巴克北京新东安、星巴克王府井in88。

180分钟前两条停留分配120+40分钟，计入真实步行和buffer后余量约1.97/1.12分钟；第三条显示停留115+35分钟，余量约5.65分钟（包括显示向下取整余量）。没有手工替换首站、改变评分或篡改duration。

此为历史数据演示，不保证当前营业/通行情况。未commit/push。
