# 城市暂停键 Multi-stop Route Builder V1 算法草案

> 本文为上一轮历史草案。最新产品确认版与离线验证见 [V1离线设计定稿草案](MULTI_STOP_ROUTE_BUILDER_V1_OFFLINE_REVIEW.md)。中点dwell、角度阈值、API失败后的Anchor回退、优先三站等建议已被新规则覆盖，不得按本文旧建议实现。

日期：2026-09-28。状态：供产品评审，未实现。

本轮只读源码、v3产品表和已采集公开快照，并进行离线数学核查；不修改正式代码/测试/数据，不调用任何百度API，不commit/push。本文的建议参数不是已批准的产品规则。

## 0. 结论与规则边界

推荐：**固定首站Anchor + Family硬过滤 + 最低停留预检 + 有界贪心分支 + 真实有向路段验证**。先取得合法两站，再尝试最多三站；不做全排列全边算路，不引入综合分，不保证全局最优。

已确定：当前单地点供给、S/M/W、Mobility、排序与buffer不动；Family与dwell仅属于Multi-stop。30分钟不运行；45/60最多2站；90/120/150/180休息最多2站、散步/探索最多3站；至少2站；最多展示3条；不返程。

建议但待确认：总移动沿用0.3T上限、6/12次新增请求预算、第二站最多检查6个、最多3个两站分支、每分支最多检查2个第三站、中点目标dwell、折返阈值、路线级去重与展示优先级。Anchor失败是否尝试下一名仍未定，草案默认不自动换Anchor。

必须提前接受的结果：候选多不等于可组合；maxStops是上限；有限搜索找不到不等于全局不存在；没有合法Multi-stop时单地点推荐独立保留。

## 1. 推荐Pipeline

`已完成的单地点默认排序全量结果 + 当前Intent/起点/路线事实`
→ 时间/模式适用性检查
→ 真实分类到Family/dwell映射
→ 选择最高排名的合格Anchor
→ 不同Family与最低停留预检
→ Route Candidate Set
→ 排定少量第二站尝试顺序
→ 先读边缓存、再受预算控制地验证A→B
→ 保存合法两站前缀
→ 允许三站时有限尝试B→C
→ 完整真实时间/通勤硬验证
→ 分配dwell与已有buffer
→ 折返比较、路线级去重
→ 0~3条Multi-stop，旁边保留原单地点结果。

前置输入必须是当前Goal/当前起点的同一份snapshot。不能因旧请求晚返回，拼出新Goal地点与旧起点路线。排序/展开/React rerender不得重新运行Builder；输入变更显式取消旧run。

30分钟返回NOT_APPLICABLE，不是失败。当前若仍勾选单地点“返回起点”，建议本次不运行Multi-stop，并明确其只支持单程；不能静默忽略用户返程要求，也不能为了运行Builder修改单地点returnMode。此交互口径待产品确认。

## 2. Candidate → Route Candidate Set

输入采用**单地点算法的默认排序结果**，不是UI“距离优先/价格优先”的临时重排，也不是可见前6个。不回到供给层重搜，不为Family不足强制触发M，不放入单地点已经拒绝的POI。

逐项附加只读多地点元数据：原始排名、已验证S/M/W、Family、dwellMin/Max、canonical端点、已成功origin→POI路线。

排除无真实分类/无法映射Family、重复身份、明确关闭、其他既有硬约束不通过者。UNKNOWN不凭空判关闭；未来营业保证不能由现有字符串“未发现关闭”推导。

Anchor建议资格：当前结果中有效、Family可映射、起点路线成功，且自身dwell_min + 起点交通 + buffer已不超预算。最后一项属于“该地点自身能否成为一站”，建议明确确认为Anchor资格；**不得把“找不到伙伴”偷偷解释成无资格并自动跳到下一名**。

确定A后，删除与A同Family的备选；用已知t(O,A)+min(A)+min(B)+buffer及已知路线事实做必然超时预检。按剩余Family分桶。K表示此时包含A的候选总数。

不再对整个池硬取“前6名”：可能全被同一个Family占据。K仍可较大，但API访问只使用下述有限提案队列。几何/top-k未检查的地点记为UNEXPLORED，不当作不合格POI，也不删除单地点结果。

## 3. Anchor后如何找第二站

为每个不同Family建立最多两名首轮提案：该Family中单地点排名最高者，以及距A直线最近者；两者相同时不重复。这里只决定探索顺序，不重写POI排序或Goal Match。

第一轮先覆盖各Family的最高排名提案；第二轮再尝试各Family的几何最近提案。每轮先无明显折返者，再按已有单地点排名，稳定身份作最终确定性顺序。建议最多检查Q2=min(6,K-1)个不同B。未进入提案的POI保持UNEXPLORED。

每个B先查可复用A→B。命中后立即用真实秒数验证；未命中且仍有预算才请求。成功但超通勤/时间上限，只拒绝该组合。缓存不作为路线优劣因子，不因为“缓存恰好有3条”就直接结束固定提案队列。

时间预检必须在读远端缓存/API之前；已知dwell就不可能放下时新增调用为0。有效第二站不止一个时保留候选分支，避免纯贪心第一个B阻断更好的第三站。

## 4. 三站如何找第三站

先保留所有已验证两站前缀。建议选最多H=3个代表前缀用于扩展，优先覆盖不同B Family，之后按折返较少、B既有排名较高选择；H小于3完全合法。

对每个O→A→B，C不能与A/B身份或Family相同。先检查t(O,A)+t(A,B)+min(A)+min(B)+min(C)+buffer；若已超预算，无需B→C请求。通勤已耗尽也不能继续。

第三站提案采用“不同剩余Family的既有排名代表/距B最近代表”，建议每分支最多检查Q3=2个C；尽量先覆盖不同Family。只追加B→C，不在V1移动Anchor、反转A/B或同时试所有插入位置。

每条合法三站都保留它已验证的两站前缀。第三站失败、时间超限或预算耗尽，直接使用两站，不重新查询已有边。

建议同一分支在第三站真实可行且没有新增明显折返时，以三站作为该分支的可选代表；否则保留两站。**“合法扩展是否优先于更宽松的两站”仍需产品确认**：它不是现有maxStops规则自动推出的结论。未确认前同时保留两种内部提案，不能擅自加“站数越多越好”的评分。

## 6. Dwell实际分配：建议采用有上限的中点目标

先用min判断路线能否存在，最终边都验证后才分配。不得复用单地点“剩余时间全给该站”的flexible停留结果；读取POI与排名，忽略单地点分配的stayMinutes。

仅知道区间不能唯一决定停留；必须显式选一个产品分配政策。比较：全给min最简单但长时间体验偏短；一直填到max容易赶场/消灭余量；把剩余时间全给Anchor会让其他站长期停在min。

建议目标q_i为区间中点向下取5分钟整档，例如30–60→45，25–50→35，15–40→25，40–90→65。这是待确认的**多地点时间分配策略，不是新分数、API事实或单地点规则**。

令T为分钟预算、W为真实移动分钟、B为现有buffer、a_i/b_i为min/max：

`D = T - W - B`

`D < Σa_i` → infeasible；否则`E = D - Σa_i`，`h_i = q_i - a_i`。

`λ = min(1, E / Σh_i)`；若Σh_i=0则λ=0。

`dwell_i = a_i + 5 × floor(λ × h_i / 5)`。

因此每站始终在[min,max]内；按相同目标完成比例分配，不优待某Family，不用评分/价格改变停留。取整只向下，零头留作自由余量，不改变原buffer。达到各站目标后不继续填满；max是上限，不是默认必须到达值。未来若用户调整停留可在区间内另做预算校验，但不属于V1本轮设计。

例：120分钟，公园+书店，真实移动20，buffer10。min合计45，目标45+25=70，实际总时间100，保留20分钟自由余量。不会为了100%利用率把两站都塞到max。

若预算刚好只够min，输出min并保留精确时间；不要因数字不好看取整加时，也不要暗中给猫咖59分钟。是否接受“全部处于min”的三站优于两站，是第4节的待决产品问题，不能自行设新舒适度硬门槛。

## 7. 时间、通勤与硬可行性

复用当前函数`bufferForBudget(T)=max(3,min(10,round(T/10)))`：30/45/60/90/120/150/180对应3/5/6/9/10/10/10分钟。一条路线只计一次，不给每段重复加buffer。

建议把现有open-ended通勤上限应用于**整条路线总移动**：

`W = [t(O,A) + t(A,B) + optional t(B,C)] / 60`

`W ≤ (T/4) × 1.2 = 0.3T`

`W + Σdwell_i + bufferForBudget(T) ≤ T`

有显式maxWalkingMinutes MUST则W还须通过该上限。不开启Goal动态比例。baseline仍为0.25T，120%上限仍为0.3T；不创建新的Mobility总分。把0.3T分别给每条边会暗中放宽整体通勤，不能这样实现。总移动口径是本草案的推荐解释，需产品确认。

45/60/90/120/150/180最大总移动分别13.5/18/27/36/45/54分钟。某个POI通过单地点可达性，不代表整个多段路线通过总移动。

构造前可使用真实已知边+未知边非负的乐观下界进行不可能性证明；比如t(O,A)+minA+minB+buffer>T，无需查A→B。三站同理。最终必须全部边成功且同源、同模式、同canonical端点，不能用失败边、反向边、直线估时或坐标标签改写代替。

仍继承地点与MUST硬约束。当前单地点营业实现只是识别明确关闭字符串，没有完整到达时营业窗口引擎。Multi-stop不应把它宣传为“已验证抵达时营业”；有可靠可解析时间才可校验预计到达/离开，UNKNOWN维持UNKNOWN。这一能力缺口及其对缩短前站停留的影响须单列决定。

## 8. 折返检测与惩罚

建议使用局部转向角，不请求新API。将同一BD-09局部坐标作一致的局部平面投影，只用于几何诊断，不改变任何Route端点。

对每个连续三点X,Y,Z，u=Y-X，v=Z-Y。若任一几何段短于建议的50m噪声阈值，不判断方向；否则若`dot(u,v)/(|u||v|) ≤ -0.5`，即转向≥120°，记录一次明显折返。两站检查O,A,B；三站再检查A,B,C。120°与50m均为待确认的解释性阈值。

输出turnCount及可读说明：“第二段方向明显返回来时方向”。必要时记录`|XY|+|YZ|-|XZ|`作为诊断距离差，不把它伪装成路网绕行距离。

Penalty不用加权总分：对均已通过硬约束的提案，先少折返，再沿用配套地点的单地点排名作为确定性比较。折返只是降序，不直接判不可行；没有其他路线时仍可展示并说明。围墙/河流可能迫使真实路线绕行，不能靠三个坐标宣称实际道路反复走过；无需复杂地图匹配。

## 9. 直线距离何时使用、何时不能使用

用途：按Family挑几何近邻提案、给下一段的API尝试排序、计算方向折返、展示“几何近但路网未验证”的内部诊断。先用坐标做便宜筛选，再用真实路线确认。

只凭几何可以做启发式top-k淘汰，但不能证明被截断组合时间不可行。没有已批准的最大步行距离或可信速度上界时，不得用“直线距离/4.5km/h超过预算”作硬拒绝。本项目当前通勤约束是分钟，不是米，不能擅自再造一套搜索半径/速度门禁。

能安全硬剪枝的是重复身份、相同Family、已知关闭、已知边及dwell_min已超时等事实；这些多数不依赖几何。若以后有明确距离MUST，可用直线距离作为路程乐观下界，但入口吸附等仍需同一端点语义。

## 10. 何时必须真实Route API

只有以下条件都通过后，才为缺失边发请求：候选真实且合格、Family不同、最低停留尚有可能、进入有限提案队列、无可复用成功边、请求预算尚有余额、当前run未取消。

一个两站方案需要O→A、A→B两条真实成功有向边；三站需要再加B→C，总共三条。不请求末站→O。O→B已有结果不能替代A→B，也不能用两条起点路线相减。相反方向必须分别验证。

单地点结果通常已提供O→A，因此两站最少**新增1条**、三站最少**新增2条**；全部边缓存有效时新增0。若没有可复用O→A，冷启动最低分别2、3条。这是证明一条方案所需边数，不是保证找到方案的请求数。

本轮不调用百度，也不假定支持自动步行途经点排序。批量矩阵仅作为未来运输优化，不作为V1可行性的前提；批量HTTP数与OD计费数必须分开。

## 11. API预算、最坏请求数与推荐数值

计数约定：K含固定Anchor，n=K-1；表中“新增”假定O→A已在单地点结果中。所有失败/超时/取消后已发出的请求也计数；不自动重试，同一run不重复请求同一边。

|方案|两站最坏新增边|三站最坏新增边|特点|
|---|---:|---:|---|
|固定Anchor、全枚举、按唯一边缓存|K-1|(K-1)^2|三站含A→各点及其他点两两有向边，不推荐|
|严格单分支greedy，依次尝试直到成功|K-1|2K-3|可能走入死胡同，输出一条，需外加硬预算|
|已有两站后做所有追加/插入位置|K-1|3K-5|三站数含建立两站时全部A出边；冷启动加1|
|有界分支Q2/H/Q3|≤min(K-1,Q2)|≤min((K-1)^2,Q2+H×Q3)|可输出不同分支，推荐|

三站全枚举只有固定A时也有n(n-1)个排列。若连Anchor都放开，唯一边上界是K条起点边+K(K-1)条POI间边=K²；不缓存重复边会更糟。K=20时，固定Anchor三站已达361条新增边，不是“只查20个点”。上述唯一边公式已用合成集合离线枚举核对。

建议待批准参数：**两站模式6次，三站模式12次新增本地Route请求，按一次生成的全部Multi-stop共享**，不是每条展示结果各6/12，也不是每换Anchor重新计数。

参考调度：Q2≤6；H≤3；Q3≤2。O→A通常复用。若须重取起点边，其1次也占6/12预算，后续提案数量相应减少；不得变成7/13。两站阶段至多用6个请求名额；三站阶段只用剩余名额。局部缓存命中0请求，服务端缓存命中的本地HTTP保守计1次（它可能没有真正消耗百度额度）。

通过统一BudgetLedger在发请求前预留名额，所有分支/Anchor共用，不并发各自透支。复用已有串行400ms节奏；增加wall-clock deadline作为独立运行限制，超时后保留已完成路线。6/12次只是上限，不承诺必定找到路线或凑满3条。

**关键成本边界**：当前单地点prepareRealPlan对保留候选逐一查起点路线，routeValidationBudget仍是Infinity。本轮不改它，因此完整用户操作上界不是6/12，而是原单地点请求数+Multi-stop新增≤6/12。需要“整体生成总budget”属于另一个产品范围，不能暗中截断单地点输入。

成本统计建议分为单地点上游、Multi-stop本地cache hit、共享pending、代理调用、provider调用（若服务端可观测）、失败、重试0、未检查提案。不得用缓存概率承诺固定计费数。

## 12. Edge cache与现有缓存兼容

已存在：客户端Map以JSON.stringify([mode,from,to])缓存成功RouteResult，无独立TTL；发现更新时可能清空。服务端按endpoint路径及请求参数缓存，含destinationUid，5分钟TTL，最多128条，pending合并，串行400ms。客户端结果不包含请求策略/观察时间，不能把任意历史Map条目一律视作新鲜。

可复用同一生成snapshot刚验证的O→A及既有服务端代理。多地点不要直接再调prepareRealPlan，否则可能再次遍历整个单地点候选池。

建议新增route-builder专用EdgeRepository包装，不改canonical RouteResult：

`provider + mode + coordinateSystem + ordered(fromId,fromCoordinate,toId,toCoordinate) + destinationUid + endpoint/entrancePolicyVersion`

结果外包observedAt/expiresAt/requestFingerprint。名字、Goal、时间预算、单地点排名不进入edge key；方向、坐标、导航入口策略必须进入。不要把几百米内坐标合并为同一个key。服务端当前请求数值会toFixed(6)，可记录该精度契约，但不能在客户端额外粗化端点。

新建持久复用条目建议沿用5分钟时效；缺少时间和请求参数证据的旧缓存只能在已确认同一snapshot下使用，不能无限期跨位置/入口策略复用。路线预算改变只重判可行性，不重算同一有效边。

no_route在本run内记忆，避免同边重复尝试；timeout/provider_error是未知，不缓存成不可达。共享同一在途Promise。位置/Goal变更取消旧run但不把已发请求从计数中抹掉。新模块的缓存不能改变原单地点缓存行为。

## 13. 失败与3→2降级

三站失败优先返回原合法两站前缀；两站失败不返回一站Multi-stop。不修改独立单地点列表，也不伪装成“单站多地点策略”。

建议结果结构将route列表与搜索完成性分离：

- OK：有真实合法路线，可同时标记搜索未穷尽。
- NOT_APPLICABLE：30分钟或Multi-stop不支持的模式。
- NO_FEASIBLE_MULTI_STOP_ROUTE：在当前供给及固定Anchor范围内有证明，例如只有一个Family、所有不同Family的min组合都超时；或相关边全部确认不可达且该有限集合已经穷尽。
- NO_VERIFIED_MULTI_STOP_ROUTE：预算/top-k/时限导致尚未穷尽，当前没找到，不能宣称不存在。
- ROUTE_SERVICE_UNAVAILABLE：关键边全是timeout/provider_error，不能冒充time不足或no_route。

输出scope={snapshot,anchorPolicy,rcsCount,examinedCount,unexploredCount,apiBudgetUsed}，只在审计中显示必要汇总，不泄露定位/UID/凭证。UI可以统一说“暂未生成多地点路线，单地点方案仍可使用”，但原因必须区分。

若固定Anchor无两站，是否尝试第二名见第18节；当前不得自动搜索新POI、降低dwell、合并同Family或绕过Travel Gate挽救结果。

## 14. 最多3条真实不同的结果

建议不引入route总分：先少明显折返，再按第二站既有单地点排名；两条均为三站且第二站相同时，再按第三站既有排名；完全相同使用稳定ID，不以时间利用率、站数或价格累加造新分。

同一两站前缀的两站/三站代表选择按第4节建议交产品确认，不能因语言默认字典序而意外永远选两站或永远选三站。

轻量去重提案：

1. 相同无序POI集合只留一个真实顺序；A→B与B→A属于同一体验集合。固定首Anchor已经避免多数反转。
2. 对共享Anchor的路线，剔除共同Anchor后，若非Anchor POI有重合，则视为高度重合，只留一个。例如A→B和A→B→C不能同时占展示名额。
3. 再比较非Anchor Family集合：相同或一方为另一方子集，只留一个。A→公园1与A→公园2不是两种体验；A→公园与A→另一公园→书店也按包含关系去重。

按已确认的展示优先级逐条放入，最多3，不为凑数放松规则。这套去重偏严格，可能只剩1条；是要明确接受的代价。可在第三站验证前减少同Family组合的重复分支，省掉注定不同时展示的尝试。若未来允许多Anchor，需要显式定义跨Anchor的无序集合与包含关系，不靠忽略不同Anchor跳过去重。

## 15. 与现有算法思想的关系

|方法|采用什么|不采用什么|
|---|---|---|
|CityWalk|候选与行程分离、增量时间、可解释站点序列|类别权重/随机必选、4.5km/h直线估时、固定dwell、直连导航|
|Greedy|围绕已选Anchor按有限队列向后扩展|只押注一个B且失败即结束、无限尝试|
|Cheapest insertion|“增加一站的增量成本”思想；缓存边可辅助解释|V1不重排Anchor，不全试插入位置；A→C→B需两条新边，明显更贵|
|Orienteering|认识到是时间约束下的选点+顺序问题，而非访问全部点|不引入prize总分、ILP/TSP全局优化或重新定义POI效用|

V1是成本有界的局部路线构造器，不应宣传全局最优。其保留多个两站前缀的目的，是减少greedy死胡同，不是恢复Easy/Balanced/Explore。

## 16. 拟新增模块与数据结构

建议仅在未来实施时新增route-builder边界：

|模块|职责|
|---|---|
|familyPolicy|24条真实路径→11 Family+dwell区间，继承与来源|
|candidateView|读单地点结果，附加singleRank/Family，资格过滤，固定Anchor|
|geometry|直线距离/转向诊断，不产出RouteResult或可行时间|
|edgeRepository|真实有向边、metadata cache、pending合并|
|budgetLedger|每run共享计数、截止时间、取消，禁止分支透支|
|builder|两站构造、有限三站扩展、保留两站前缀|
|dwellAllocator|只对最终路线分配[min,max]内停留|
|routeSelection|折返比较、集合去重、最多3条|
|routeAudit|拒绝原因、已证实/未检查/服务失败、额度归因|

数据结构建议：RouteCandidate、FamilyRule、DirectedEdgeKey、CachedEdge、RouteDraft、VerifiedMultiStopRoute、MultiStopBuildResult。VerifiedMultiStopRoute的stopCount只能2或3、endMode固定open_ended、routes均成功，含逐站dwell/remaining/buffer/backtrackDiagnostics；禁止复用单地点strategyId命名旧三策略。routes不是任意列表，要保证相邻端点连续。

接口应接收完整单地点结果/Intent/原snapshot及只读路线事实，返回独立multiStopRoutes；不能原地改写CandidatePlan的stayMinutes或places数组。不得把Family/dwell写回MapPOI，避免把产品政策伪装成百度属性。

## 17. 哪些现有代码不需改

v3表与discoverGoalCandidates、Web Search分页/分类验证/每标签5个、单地点realProvider、buildDecisionResult/compareRecommendations、Mobility公式、Rating/Price比较、bufferForBudget、现有单地点排序及“前6+更多”都不需要改算法。

复用map.ts的MapPOI/RouteResult与现有固定Direction代理；不需要新AK或新搜索接口。未来只需在编排/UI边界增加独立Builder调用和结果区域，并添加请求元数据包装以安全复用缓存；这与“修改单地点算法”分开评审。本轮没有执行这些变更。

## 18. 实现前产品决策与Anchor取舍

|Anchor政策|工作量|API成本|质量/风险|
|---|---|---|---|
|固定最高合格排名1名|最小，单run|≤6/12|最符合当前规则；可能漏掉第二名可组合路线|
|首名找不到两站后允许第2名|增加资格/失败原因与共享预算状态|共用6/12不增加硬上限，但每名探索更浅|改善僵局；会牺牲第一名的部分搜索广度|
|允许前3名依次尝试|实现增量不大，测试/解释组合更多|共享6/12，或若每名重置会错误膨胀到18/36|覆盖更广，但容易每名只试少量边，仍没有完整性|

不能在第一名用完全部预算后才承诺第二名仍可尝试。若批准最多2名，可讨论两站预算4+2分配；三站先为两名各保留最多4次寻找两站机会，剩余最多4次扩展第三站。若第一名已有合法两站，即使无三站，也不要只为凑三站换Anchor。以上只是备选，**当前不自动启用**。

只因所有候选同Family或全局dwell下界不可能，换Anchor也无用，直接0调用退出。最高Anchor因自身min都放不下而不合格，与最高合格Anchor没有伙伴必须在审计中分开，防止变相自动fallback。

我的建议：可以批准“仅在首Anchor没有任何已验证两站时，最多尝试第2名，共享budget”；但这确实放宽现有固定Anchor原则，必须由产品选择。若不批准，接受局部无结果，不偷偷遍历全部Anchor。

其余必须确认：

1. 总移动用0.3T，还是产品另有对现有规则的解释；不引入Goal差异比例。
2. 6/12 budget、Q2/H/Q3、wall-clock deadline和是否允许每次显式再试；单地点成本单独核算。
3. 中点目标dwell与5分钟向下取整；合法三站是否优先作为同分支代表。
4. 折返120°/50m与先少折返的展示顺序；Family/包含关系去重严格度。
5. 用户仍勾返程时Multi-stop入口怎么解释；不静默忽略MUST。
6. 营业窗口UNKNOWN展示标准；是否在未来加入抵达时校验（当前没有完整引擎）。
7. “随心安排”目前解析到具体activity但v3产品文件仍注明需另定；Builder只消费已解析Goal，不新增flexible Family规则或推断。
8. 是否接受45/60分钟经常无多地点。如果不接受，最小变更是明确按Family调整**多地点**min，或增加用户批准的短停留体验规则；不能减少buffer、伪造步行、自动降级为单站来掩盖。
9. 若真实供给只有一个Family，是否未来允许独立“多地点补充召回”；这会改变供给行为，与本轮保持v3不动冲突，当前禁止实现。

## 附录B：可证明的时间边界

文化观展40 + 兴趣/日常零售15 + 60分钟buffer6 = 61，零交通都失败。文化Anchor在45/60多地点不能成立。

休憩饮食30 + 兴趣零售15 + 45分钟buffer5 = 50，因此休息类Anchor的45分钟通常无两站。散步绿色30与最短兴趣零售15在45分钟同样失败。45分钟探索若是两个不同零售Family则30+5，理论仍可有10分钟移动，但它们必须已经在当前白名单供给与单地点结果中，不能为此额外召回。

公园30 + 书店15 + 60分钟buffer6 = 51，最多还可9分钟总移动；该组合不必然失败。公园30 + 商业漫游25 + buffer6 = 61，60分钟必然失败。

公园30 + 文化40 + 书店15 + 90分钟buffer9 = 94，因此三站不可能，但其中公园+书店的两站可能。90分钟的三站不是一概不可能，例如兴趣零售15+日常零售15+商业漫游25+buffer9=64，仍有26分钟总移动空间（同时受27分钟gate）。

猫咖60 + 兴趣零售15 + 90分钟buffer9 = 84，仅剩6分钟总移动。不要通过给猫咖分配低于60来“救活”路线。

这些是零交通或已知前缀的乐观下界；下界通过仅表示值得考虑，不是路线可行证据。

## 附录C：当前真实快照的离线压力检查

未调用百度，仅对现有65个公开候选与起点路线读取Family及默认单地点结果：

- 休息池13个地点只有休憩饮食7、书咖5、猫咖1。45/60的单地点可行结果各只有1个，没有不同Family伙伴；即便放宽到完整供给池，最短两Family停留也是60，再加buffer即超过60。
- 散步池22个：绿色14、商业5、购物中心1、休憩饮食2。45/60可行单地点各2个，均为绿色，不能组合；90分钟虽有不同Family伙伴，三站最短Family组合为25+30+30+buffer9=94，仍必然退到至多两站。
- 探索池30个：全部文化观展。45~180所有档都不可能满足两Family，属于供给结构问题，与API错误或Builder搜索能力无关。
