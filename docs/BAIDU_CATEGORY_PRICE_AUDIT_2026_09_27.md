# 百度分类与价格来源审计

日期：2026-09-27。本轮只审计代码及官方公开资料，不操作用户页面、不调用真实地点/路线 API、不改推荐规则。

## 候选分类 UNKNOWN、方案有分类

- LocalSearch Adapter 只读取 JS API 的 poi.tags；未返回数组时 categories 保持 undefined。来源：src/map/poiAdapter.ts 的 adaptBaiduLocalResultPoi。
- DiscoveryPanel 显示搜索快照中的 categories 和 samples.providerCategories。UNKNOWN 只代表该次搜索结果未带可用分类，不代表百度没有分类。
- prepareRealPlan 对候选副本加载 Place Detail，再用 mergeBaiduPlaceDetail 合并 detail_info.tag 与 classified_poi_tag。原 discovery snapshot 不回写。
- PlaceDetails 展开时也可独立加载详情，因此即使推荐准备时详情失败，稍后详情成功后也可能展示更多资料。
- 这解释了不同区域的信息差异：不是从需求或名称猜分类，而是不同阶段的数据未统一展示。

## 费用未知、详情有商户价格

真实字段链：百度 detail_info.price -> 服务端 price -> MapPOI.priceText。有效纯数值经 merchantPrice 解析后，已经进入 Pareto price 维度和默认排序。

但 REAL Provider 故意不推断 costRequired。engine 的 costStatus 只看 costRequired；evidence.placeCost 只认可显式费用声明或“免费开放/免费入场/免门票”原文，普通数值价格仍返回低消费证据 UNKNOWN。engine 随后无条件把这种 UNKNOWN 写成“费用信息未知，请先查看详情或电话确认。”，即使 merchant price 已知。

结论：有价格却显示费用全未知是提示口径错误，不能据此判断 API 不支持价格。商户价格已知与本次是否必须消费是两件事。合理展示应分别说明商户价格，以及必需消费/门票是否明确；不能将数值价格推导成免费或必须消费。本轮未修改提示或决策。

额外发现：Planner 的用户主动“价格优先”目前只区分有无 priceText，并未按数值高低排序；默认推荐比较器已经使用数值价格。该问题本轮只记录，未修改。

## 官方分类来源与完整性

1. [官方 POI 行业分类](https://lbs.baidu.com/index.php?title=open/poitags)：31 个一级分类，一级/二级全集转录于下表。包含道路、界线等地图要素，并非全部适合作为游玩候选。
2. [官方地点检索 V3 文档](https://lbs.baidu.com/faq/api?title=webapi/guide/webservice-placeapiV3)：明确链接上一份行业分类作为搜索参考，并给 classified_poi_tag 链接另一份“POI 展示分类表”。
3. [官方 POI 展示分类 Excel](https://mapopen-website-wiki.cdn.bcebos.com/static/doc/POI%E5%B1%95%E7%A4%BA%E5%88%86%E7%B1%BB%E8%A1%A8.xlsx)：32 个一级分类、最多五级、1485 条非空分类行。全文见 [展示分类全集](./BAIDU_POI_DISPLAY_TAXONOMY_2026_09_27.md)。这是公开目录的全集转录，不是对全部内部标签的完整性承诺。

两表不能混用。例如行业表的咖啡厅同级包含“蛋糕甜品店、茶座、酒吧”，展示表在美食二级中使用“甜品店、饮品店、糕点烘焙”等。行业表把美术馆放在文化传媒，展示表放在旅游景点。

当前项目把 tag、classified_poi_tag 合并，再按 / 和 ; 拆成平铺 categories，丢失字段来源与层级边界。为后续 Goal Match 设计，应保留字段来源、完整分类路径及缺失状态，再使用经产品确认的规则。不要直接把现有扁平字符串当成同一套分级标签。本轮没有添加类别权重或 Goal Match 映射。
